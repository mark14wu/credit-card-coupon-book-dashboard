# Setup playbook for Muse

You are setting up the Credit Card Coupon Book Dashboard for your user from this repository. Follow these steps in order. Do not skip the questions in steps 3 and 5.

## 1. Create the app

Create a private web artifact (full-stack) in the user's workspace with slug `credit-card-coupon-book-dashboard`, using the source in this repository (`client/`, `server/`, `drizzle/`, `package.json`) as the app's code. Do not invent a different implementation — the value of this repo is its tested data logic (merge-only import, transaction-date attribution, catalog matching).

If the user already has an artifact with that slug, stop and ask before replacing anything.

## 2. Connect Plaid

The app's data comes from the Plaid connector. Check whether the user has Plaid connected; if not, walk them through connecting it and linking their American Express login(s). Households commonly have **two** Amex logins (e.g. the user and their spouse) — link both if they exist, and expect up to one login per person per issuer overall. If the user also holds Chase cards with coupon-book credits (Sapphire Preferred, World of Hyatt Business, IHG One Rewards Premier, Ritz-Carlton), link the Chase login too — the catalog covers those products, including their anniversary-year cycles. If the user holds the U.S. Bank Altitude Reserve, link the U.S. Bank login too — but read the identification bullet in step 4 first: U.S. Bank's Plaid account names are generic, so that card is recognized by evidence (its $400 annual fee and its credit postings), never by name.

Supported cards are exactly the ten listed under "Supported cards (verified)" in the README — "verified" means the card has catalog definitions in this repo **and** unit tests pinning them down. Any other card is not yet supported — in particular, Chase United cards (e.g. United Explorer) have not been verified: their accounts may appear via Plaid, but no credits are tracked for them. If the user wants another card supported, that is a contribution: add its catalog definitions **and** unit tests, run `bun test` and `bun run typecheck`, and open a pull request (see "Contributing" in the README) — do not improvise a catalog entry without tests.

Do not ask for, accept, or store Amex usernames/passwords yourself. The connection happens through the connector's own flow.

If Plaid turns out not to be connected at all, stop here: run the Plaid connector's status check, post the connect link it gives you, and wait for the user to finish linking before doing anything else — then check status again before importing. Never substitute the repo's fictional test fixtures, sample data, or hand-typed numbers for a real connection; a dashboard built on invented data is worse than no dashboard. Linking additional institutions (a spouse's login, a Chase login) uses the connector's add-account flow — one institution per link session — so repeat it once per login.

A linked login can also stop working later: banks periodically require re-authentication, and a login in that state returns no data. That surfaces during refresh, not setup — see step 6 for how to spot it and what to tell the user.

## 3. Ask: whose logins are these?

Every account carries an owner key, and the key names a **person, not a login**. Only two keys have display labels — `A` and `B` (defaults "Login 1" / "Login 2"). A person with logins at two issuers (their own Amex login **and** their own Chase login) uses the **same key for both**; the dashboard groups that person's cards by issuer under the one label. Households commonly link three or four logins (two people × Amex + Chase) — map every login to one of the two people, and never invent extra keys (`C`, `D`, …): accounts carrying an unknown key surface under "login not identified yet" with no label. A one-person household simply uses `A` for everything. The rule is per **person**, not per login or per issuer: when a person links an additional login later (say person A's U.S. Bank login, on top of their Amex and Chase logins), that login reuses the same key — `A` stays `A` no matter how many logins it covers.

Ask the user whose each login is and what label each person should get — typically their first name and their spouse's first name. Save the answers with the `setOwnerLabels` action (meta keys `ownerALabel` / `ownerBLabel`); the user can also edit them later in the page's Cards section ("Login labels").

**Timing: labels do not have to be settled before the first import.** They are plain meta values and can be set or corrected at any time. It is often easier after the import in step 4, when the accounts are visible — a distinctive card in a login (e.g. a Morgan Stanley Platinum) often settles whose login it is. What has to be right is the owner key on each account. Attribution is **sticky**: an import only fills an account's owner when it has none yet and **never overwrites** an existing one, and the refresh agent attributes logins to people from account evidence (cardholder names, products), leaving `owner` unset when it cannot tell — never by a grouping's position in the Plaid output. After the first import, check every account's owner in `getDashboard`; if a login landed under the wrong person, correct it with the `updateAccount` action (`{ accountId, owner }`) — re-importing with a different owner will NOT move it — or let the user fix it in the page's Cards section, then re-check.

Within one person, cards are told apart by the automatic product prefix (Aspire, BusPlat, BusGold, …), the card name, and the card's ending, shown as owner label + ending (e.g. `Alex 1234`). Two cards of one person's can share the same product **and** the same last four — told apart then by the **fifth digit** (the digit before the last four): the issuer's app shows a five-digit ending (e.g. 41003 vs 81003), so ask the user for each card's fifth digit and record it with `updateAccount` (`{ accountId, fifthDigit }`, a single character `0`–`9`; the user can also enter it in the Cards section). Labels then read `Alex 41003`, and once two same-ending cards' five-digit endings differ they stop being flagged as possible duplicates (step 4). A card belonging to the *other* person is never flagged against this person's cards and needs no digit — the owner label already distinguishes it. Each account can also carry a user-set **nickname** (a short display prefix such as `UA`): set it with `updateAccount` (`{ accountId, nickname }`) or in the Cards section ("Set prefix"). When a nickname exists it replaces the automatic prefix on credit rows and in the Agent Markdown; imports never overwrite nicknames or fifth digits.

Never hardcode names into code. Labels live in app meta only.

## 4. First import (bootstrap) and reconciliation

Open the app and trigger `refreshCredits`. With an empty database it performs a bootstrap pull from **January 1 of the current year** to today — or from the start of the earliest current anniversary period when an anchored credit's period began last year — imports all accounts and credit postings, and records the coverage start.

How many accounts appear varies by household — every card record on every linked login shows up. **Nothing is deduplicated automatically**: a supplementary (authorized-user) record of a primary account shows up as its own account, and duplicates are never auto-ignored. Records that look like two views of one card (same product + same ending within one person, or one record's transactions appearing under another) are flagged `suspectedDuplicate` in `getDashboard` and wait for a **user decision**: once the user confirms two records are the same card, mark the supplementary one ignored with `setAccountIgnored` (the user can also do this in the Cards section). When a flagged pair turns out to be two genuinely separate cards of one person sharing an ending, resolve it the other way: ask the user for each card's fifth digit (visible in their issuer's app as the five-digit ending) and record them with `updateAccount` — different five-digit endings clear the flag. Until then both records count in every total — that double-count is deliberate, because only the user can tell a duplicate record from a second, genuinely separate card of the same product.

Then pull `getDashboard` and reconcile before telling the user setup is done. Report:

- **Accounts per person** — how many tracked cards sit under each login label, any records flagged as possible duplicates (ask the user whether each flagged pair is one card or two before marking anything ignored; if a pair is two separate cards sharing an ending, ask for each card's fifth digit from their issuer app and record it via `updateAccount` per step 3 instead), and any account sitting under "login not identified yet" (its owner key is missing or wrong — fix it per step 3 before going further).
- **The headline numbers** — total unused (`totals.remainingNow`) and how many open credits it spans. Expect the same product on both people's cards (two Sapphire Preferreds, two sets of Aspires) whenever both hold it: that is normal — the rows are the same credit name told apart by owner label and mask, and the totals combine both people by design.
- **Anniversary anchors** — the Sapphire Preferred hotel credit and the World of Hyatt Business credit are seeded with the catalog's **default anchor, May 1**. (The Hilton Aspire resort credit is not anchored: Amex runs it on calendar halves, January–June and July–December.) That date is a placeholder, not something read from the user's account: seeded anchors are stored **unconfirmed** (`anchorConfirmed: false`), the credits carry an "anchor unconfirmed" flag in the page, and the Agent Markdown lists them under "Warnings — needs your decision" until resolved. Ask for each such card's real anniversary month and day and fix the anchor on that credit — the credit's edit form in the page ("Anniversary anchor"), or `updateCredit` with `anchorMonth` / `anchorDay` (month and day are a pair — both or neither; setting either marks the anchor confirmed). When the May 1 default happens to be right, confirm it as-is with the credit's "Confirm anchor" button or `updateCredit` with `anchorConfirmed: true`. Anchors are per credit, so the two people's cards can legitimately differ.
- **U.S. Bank Altitude Reserve (generic Plaid names)** — U.S. Bank reports generic account names (e.g. `Credit Card - 7536`), so no catalog fires for the account and no credit is seeded automatically. Identify the card by evidence in its own transactions: a **$400 annual membership fee** posting, and small postings named **`Annual Travel/dining Credit (up To $325)`** (under the current policy the bank reimburses each qualifying travel purchase booked through the U.S. Bank Travel Center separately, up to $325 per cardmember year — dining was covered in earlier cardmember years, which is why the postings carry that name). When both are present, the account is an Altitude Reserve: create its credit with `addCredit` from the catalog definition — name `Travel Credit`, amount 325, period `annual`, matchPattern `travel/dining credit` — with `anchorMonth` / `anchorDay` set to the annual-fee posting's month and day, because the cycle is the cardmember year anchored on that fee date (an anchor taken from the user's real fee posting is confirmed by definition, so no separate confirmation step is needed). The bootstrap import ran before the row existed, so this cardmember year's already-imported `Annual Travel/dining Credit` postings are sitting in Unassigned: attach each of them to the new credit with `assignPosting` (see the Unassigned bullet below); later refreshes auto-file new ones by pattern. Postings named `Real-time Rewards Credit` are points redemptions, **not** this credit — never map them; leave them unassigned.
- **Credits showing $0 used that the user expected to see used** — check the credit's `currentPostings` and compare its `matchPattern` against the actual posting names (the Agent Markdown lists each credit's postings). The usual cause is a posting name the pattern does not match; fix the pattern on the credit (`updateCredit`) rather than adjusting any amounts.
- **Unassigned postings** — say how many entries sit in `getDashboard`'s `unassigned` list. Postings belonging to the synthesized families (ChatGPT Business and the other default-hidden ones) are already counted automatically at read time and never appear there; what remains is genuinely unmatched. Walk through it with the user: attach a stray posting to its credit with `assignPosting`, and if a recurring credit the catalog does not know keeps stranding postings, add it with `addCredit` (name + match pattern) so future imports file its postings automatically.
- **Enrollment** — tracking is not enrollment. Some credits only pay out after the holder activates them with the issuer: read the visible credits' `note` fields and list for the user the ones that say so (e.g. ChatGPT Business enrolls separately per card; Resy, Equinox, Digital Entertainment, and Walmart+ require enrollment; the airline fee credit needs an airline selected first; the Ritz-Carlton travel credit is claimed manually after the purchase). The dashboard tracks these credits either way — until the user enrolls, the money simply never posts. Each credit carries an `enrolled` flag, flippable in the page or via `updateCredit`. Enrollment is **never assumed either way**: the dashboard cannot observe whether the holder actually enrolled with the issuer, so credits whose benefit requires it are seeded (and synthesized) as *unconfirmed* (`enrolled: null`) and stay flagged in the page and in the Agent Markdown warnings until the user says whether they enrolled — ask, and set the flag (`true`/`false`) only when the user tells you the actual state.

## 5. Ask: which credits to hide?

Some credits are hidden by default — the built-in list covers ChatGPT Business, Indeed, Adobe, CLEAR+, Equinox, Digital Entertainment, Walmart+, and Instacart. Hidden credits never appear on the dashboard and never count in any total. They do not need a stored database row to exist: the dashboard synthesizes every catalog credit for every account at read time (a stored row, when present, supplies the saved state and its postings still count as assigned), so removing a credit's entry from the preference below always brings it back — even on accounts imported before that credit family was tracked.

Hiding is a **stored preference, not a code setting**: it lives in the app's meta table under the key `excludedCredits` (a JSON list of lowercase name patterns). The user can change it themselves in the web page's Display settings section (one toggle per hideable family) or by asking you in chat — both paths go through the same two actions below, and a selection the user saves is authoritative (the built-in defaults only apply until something is stored):

- Read the current list with the `getPreferences` action. (When nothing has ever been stored, it returns the built-in defaults.)
- Change it with the `setExcludedCredits` action, passing the **complete** new list — it replaces the stored one, it does not append. To show a hidden credit again, resend the list without its entry; to hide another credit, add its name. An empty list shows everything.
- Entries are matched as case-insensitive substrings of credit names at read time, but **write-time validation is canonical**: an entry is accepted only when it is exactly a hideable family's pattern or label, a full catalog credit name, or a full stored credit name. Fragments like `credit` or `air` are rejected with an error — they would hide nearly everything — so if a call fails, use the family pattern or the full credit name from `getDashboard` or the catalog.

The change takes effect immediately — in the dashboard, and in the Agent Markdown export, which names the hidden credits under "Hidden by preference" so you always know they exist. Ask the user whether they want any of the default-hidden credits shown, or anything else hidden, and apply their answer with the action. Never edit source code to change the exclusion list.

## 6. Set the daily refresh (recommended)

Create a scheduled job (cron) that runs every morning and invokes the app's refresh: it pulls only the **last 30 days** from Plaid, diffs against stored postings by transaction ID, and merges — never deletes. Attribution is by transaction date: for every posting, pass the Plaid `authorized_date` as `transactionDate` alongside the posted `date` (the app buckets by `transactionDate`; a re-import may correct a stored transaction date in place). The job should stay silent while refreshes succeed — with one exception that must never stay silent: a login that needs re-authentication. When a Plaid login drops out, the refresh imports with `complete: false`: whatever could be read still merges, but `lastImportAt` does not advance and the next run retries a wider window instead of the 30-day one. If a refresh reports Plaid not connected or a login failing — or `getDashboard` shows `lastImportAt` no longer advancing day to day — tell the user promptly which login is affected and that they need to re-authenticate it through the Plaid connector (the status / connect flow from step 2). Do not let the job retry in silence for weeks: the dashboard will look calm while quietly going stale.

Optionally also offer a monthly reminder (e.g. on the 24th) summarizing credits that will expire at the end of the current period with a remaining balance. Only create it if the user says yes.

## Ground rules

- Never delete stored postings during a refresh. The store only grows.
- Never place orders, book anything, or spend a credit on the user's behalf. This app observes; it does not transact.
- The user's data stays in their workspace. Do not copy it anywhere else.
